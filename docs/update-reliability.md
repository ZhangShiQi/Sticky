# 更新可靠性（2026-10-26）

本文记录 0.3.0 的更新架构、验证范围和边界；发布状态以 GitHub Releases 为准。测试使用项目中的独立临时目录，不修改用户正在使用的便签工作空间。

## 结构与提交边界

```text
Sticky.exe                     稳定、自包含启动器；正常自动更新不覆盖
tools/runtime/Sticky.exe       首次安装的 WPF 程序
tools/git、tools/gcm            首次安装的工具
versions/<version>-<id>/        完整且独立的后续版本，包含自己的程序和工具
.sticky-launcher/
  current.json[.bak]            已确认版本、前版及失败包摘要
  queued.json[.bak]             等待应用保存退出的更新请求
  pending.json[.bak]            阶段、候选版本、数据路径、子进程身份
  commits/<id>.json             独立的不可撤销提交证据
  snapshots/<id>/              数据快照及逐文件 SHA256 索引
  staging/<id>/                尚未发布为版本目录的暂存内容
Data/                          用户正文、图片、分组、本机设置
```

流程：保存并退出 → 校验完整 ZIP → 解压并校验每个组件 → 原子发布候选目录 → 完成数据快照 → 启动候选进程 → 记录其 PID/启动时间 → 私有管道验证身份 → 授权初始化 → 等待真实 WPF 窗口/正文/图片及托盘初始化、UI 空闲 → 就绪确认 → 稳定观察 → 原子写版本指针及独立提交记录 → 授权用户编辑和后台同步。

Windows Job 在提交前约束候选进程生命周期。启动器突然被结束时，未确认进程也被结束；如果进程尚未加入 Job，它仍在等待管道授权，不能初始化数据。试启动期间所有窗口不可编辑且不可见，托盘隐藏，更新/同步计时器尚未启动。管道是当前用户专用，并验证随机码和实际子进程 PID。

提交前失败：停止未确认进程、持有应用单实例锁、完整校验快照后恢复数据，再运行旧版。恢复过程中再次终止，下次从同一受保护快照重复恢复。提交后失败：保留现有数据，仅选择前一程序版本。独立提交记录防止版本指针损坏时将旧快照覆盖到提交后的编辑上。失败包按 SHA256 隔离，不会在自动检查中反复安装。

首次运行新布局也经过快照和启动确认。0.2.2 旧更新器产生的旧程序备份可作为首次失败的回退来源；先校验旧 exe 和清单，再运行已知旧版并暂停旧版自动更新。旧版不支持新启动确认协议，不能将这次兼容回退描述成新协议的完整健康确认。

## 自动测试

`Sticky.Tests` 是 STA 控制台测试项目，测试目录独立于用户 Data。`UpdateTests.cs` 有 13 组更新专项测试：版本比较、下载校验、私有认证、断网/取消/重试、包路径与组件验证、原地更新兼容回归、逐组件失败与实际文件锁、连续升级、WPF 同步上下文死锁及离线保存。

兼容安装的文件锁回归同时覆盖持续占用时安全回滚，以及原 exe / 暂存 exe 在短暂占用后释放时继续安装成功；替换和回滚的重试有 5 秒上限。

`LauncherTests.cs` 有 7 组启动器测试：

| 范围 | 验证 |
| --- | --- |
| 健康确认 | 正常、初始化崩溃、超时、发送 ready 后立即退出；内置/外置 Data |
| 12 阶段强杀 | 暂存开始、暂存完成、发布目录、快照开始、复制快照文件、快照完成、创建子进程、初始化、就绪、写版本指针、提交完成、授权编辑 |
| 恢复再中断 | 在恢复某个文件后强杀恢复进程，第三次启动恢复成功 |
| 恢复数据校验 | 损坏快照时停止写入、保留事务；修复快照后恢复成功；版本指针主文件损坏可读上一代 |
| 首次启动及兼容桥接 | 首次新布局必须确认；首次失败可运行已校验旧版，暂停旧版自动更新 |
| 后续启动失败 | 已确认程序被破坏时退回前版；升级后新增内容逐字节保留 |
| 安装前拒绝 | 不兼容数据格式/启动协议、组件被篡改、快照源文件被锁定；旧版保持可用 |

阶段测试使用真实子进程、命名管道、Windows Job 和 `Process.Kill()`，刻意不调用 kill-tree 来替 Windows Job 清理。候选程序是可控的测试协议进程，包含模拟初始化写入；不是每个强杀场景都运行真实便携 WPF exe。授权编辑后的场景额外写入新便签内容并破坏当前指针，验证独立提交记录阻止旧快照覆盖。

`PortableUpdateSmoke.cs` 则使用打包后的真实自包含 `Sticky.exe` 和 WPF 程序：

1. 原生启动器从不同工作目录启动，确认外置中文/空格/单引号 Data 中的真实富文本、图片、分组和已打开便签窗口初始化完成。
2. 实际 ZIP 经过版本目录安装、快照、WPF 就绪确认和提交，旧程序保留，稳定启动器字节不变。
3. 向真实候选进程注入错误的启动身份，验证拒绝、恢复和已确认版本重新显示窗口，并隔离失败包。

该测试在显式标记的测试 Data 中启用独立实例，不结束用户当前便签进程。首个协议版本尚无以前的同协议正式包，因此便携检查执行同版本重装事务，不等于从 GitHub 上一正式版本自动检查/下载的完整链路，也不等于已测试所有历史版本。下载和私有认证由独立 HTTP 替身测试覆盖。

```powershell
# 全量（正式发布会自动执行）
.\test.ps1 -ArtifactsPath .tools\full-check
# 更新与启动器专项
$env:STICKY_TEST_FILTER = 'Update|Launcher'
try { .\test.ps1 -ArtifactsPath .tools\update-check }
finally { Remove-Item Env:STICKY_TEST_FILTER -ErrorAction SilentlyContinue }
# 已打包文件的真实便携检查
.\scripts\test-portable-update.ps1 -Package <zip> -TestAssembly <Sticky.Tests.dll>
```

## 发布约束

`release.ps1` 必须通过完整应用测试、13 项发布流程检查、6 项发布 API/凭据检查、打包校验和真实便携检查，才可创建标签、推送和上传。设置 `STICKY_TEST_FILTER` 会被拒绝。正式发布仍使用本机资源；未增加云端构建或发布权限。

另有 3 项压缩包回归，明确通过 Windows PowerShell 5 执行：统一 ZIP 标准斜杠及保留 Unicode 内容、拒绝覆盖旧包、拒绝将 Data 打包。使用 PowerShell 7 发布时也会执行该兼容检查，避免 .NET Framework 生成反斜杠 ZIP 而在更新时被拒绝。

## 边界及恢复

- 状态文件采用同卷临时文件、写穿与 Flush(true)、原子替换，并保留上一代。阶段强杀模拟突然结束进程；没有在本机执行物理断电、磁盘拔出或真实磁盘耗尽测试，不能据此保证所有硬件/文件系统故障。
- 快照排除下载缓存 `device/updates` 和可重建的 Git 缓存 `device/sync`；正文、图片、分组、本机设置和已有备份均受保护，系统凭据不复制。快照不自动上传，不删除原文件来腾空间。
- 启动器协议和数据格式固定为 1，不兼容更新会拒绝安装。未来更改数据格式必须另行设计兼容迁移；禁止靠恢复旧快照覆盖提交后的编辑。
- 稳定启动器不会随普通版本替换。启动器协议或自身运行时升级需要专门的手动升级；不要用未验证的新启动器覆盖现有入口。
- 若事务/快照无法校验，或另一便签实例仍持有锁，停止恢复并保留现场，不猜测或删除用户数据。启动器错误在 `.sticky-launcher/launcher-error.json`，应用可见结果在 `Data/device/update-result.json`。
- 旧版本、快照和暂存内容当前保留，会占用空间。尚未提供自动清理，不能手动删除 active/previous 版本或未完成事务依赖的文件。退出且更新恢复完成后再移动/复制目录；进行中的事务包含原数据的绝对路径。
- **0.2.2 → 新布局的首次安装仍由旧更新器原地替换**，此前的强杀恢复设计无法追溯补进旧二进制。新启动器安装后可使用旧程序备份回退，但旧更新器替换入口过程被强杀，仍可能需要手动恢复。0.2.0/0.2.1 仍须手动升级一次。建议首次新布局在独立目录测试，保留原目录和 Data 备份。

目标是更新失败仍有可运行的程序、便签保持完整且恢复可重复。它不构成对磁盘损坏、外部修改、杀毒软件持续隔离或所有历史升级组合的绝对保证。
